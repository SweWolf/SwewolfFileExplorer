# SweWolf File Explorer (SwewolfFileExplorer)

A Windows File Explorer clone built with C# (.NET 10) and WPF.

## Build & Run

```bash
dotnet build
dotnet run
```

The user tests the **Release** build: after every change run `dotnet build -c Release -p:Platform=x64` (output `bin\x64\Release\net10.0-windows\SwewolfFileExplorer.exe`), so they can run it without Visual Studio.

## Architecture

- Pattern: **MVVM**. `MainWindow.xaml.cs` handles UI events only (double-click, F2, context menu clicks) and delegates all logic to `MainViewModel`.
- NuGet packages: **TagLibSharp 2.3.0** (tags of music files; same version as FileInfoViewer), **Microsoft.Data.Sqlite** (the library) and **Svg.Skia 5.2.3** (SVG pictures, with SkiaSharp and HarfBuzzSharp: about 12 MB of native code, added 2026-10-18 with the user's approval). Packages are **not forbidden:** the user said (2026-10-15) that if a package would help, ask him at that moment; he will probably say yes. Say so in advance when a feature would need one (e.g. MetadataExtractor for image EXIF, as the sibling FileInfoViewer uses).
- Target platform: **Windows x64** (`net10.0-windows`).

## Key Design Decisions

- **Icons and speed on slow drives (2026-10-17, found by the user: opening the session `Test` took about 10 s; it holds `G:\My Drive\Music\Suno`, 618 files on Google Drive, and `D:\Downloads`):** opening that tab took 4.0 s, now 0.4 s (0.24 s the second time). Measured piece by piece (a throwaway app timing `LoadItems`, `ResolveNode` ...), the causes were: (1) **every file loaded its own icon from the disk in its own `Task.Run`** (618 at once): they held up the folder listings of the tree on the same drive. Now `FileItemViewModel.LoadIconAsync` gives a file the **icon of its type** (`IconHelper.GetIconForName`, kept per extension, no disk access, as Explorer does); only a **folder** and a file with an **icon of its own** (`IconHelper.HasOwnIcon`: exe, ico, cur, ani, lnk, url, scr, icl, cpl, msc, and any type whose registry `DefaultIcon` is `%1`) are read from the disk, in the background. The first file of a type asks `IconHelper.GetIconForNameAsync` (one background lookup per extension for all files of that type, as the first lookup of a type can take 20-50 ms when the shell loads the program that owns it); later files get the cached icon at once (`TryGetCachedIconForName`). (2) The **Type text** of each file used `IconHelper.GetFileType(path)`, which asks the disk `Directory.Exists(path)` for every file (6 ms each on Google Drive): the list now uses `GetTypeNameForName(file.Name)` (per extension). (3) The **tree** read each folder up to six times (the subfolders, then once per packed-file pattern) and asked the disk for the attributes of every folder one by one (`File.GetAttributes`, about 20 ms each on Google Drive): `TreeItemViewModel.ListChildren` now reads each folder **once** (`EnumerateFileSystemInfos`, whose entries carry their attributes), also for the expand-arrow check (`HasSubDirectories`) and `CountHiddenIn`. The same listing is what the tree showed before (checked: children, expand arrows, hidden nodes, `CountHiddenIn`). **Wait cursor:** opening a session or workspace sets `Mouse.OverrideCursor = Cursors.Wait` until the tabs are open (`MainWindow.OpenTabSet`, also for a file on the command line). Not done: opening only the active tab at once and the others when first shown (it would save more for sessions with many tabs), and a wait cursor for other slow operations.
- **A click in the tree reads the folder in the background (2026-10-19, found by the user: the program hung for 10+ minutes after a click on a tree folder):** `dotnet-stack report -p <pid>` (installed globally with the user's approval) showed the UI thread inside `FileSystemEnumerator.MoveNext` < `TreeItemViewModel.CountHiddenIn` < `FolderTabViewModel.LoadItems` < `Navigate` < `NavigationTree_SelectedItemChanged`: no CPU, no disk I/O, one folder whose listing never came back (which folder is not known). Everything in `LoadItems` ran on the UI thread. **`FolderTabViewModel.NavigateAsync(path)`** (via `MainViewModel.NavigateAsync`, used by `NavigationTree_SelectedItemChanged` only) does the disk work in `Task.Run` (`ReadListing`: subfolders, files, and the tree's hidden-folder count), with "Reading folder..." in the status bar and the old list still shown; `NavigateCore` then fills the list from that listing (`LoadItems(path, preread)`; read again if the Folders button was toggled meanwhile; an error in the read ends as the usual "Access denied" / "Error: ..." text). `_navVersion` is raised by every `Navigate` / `NavigateAsync`: a click made while an earlier listing is still being read drops the earlier one (a stuck read keeps one thread-pool thread blocked until Windows answers; the window stays usable). Anything that is not a plain existing folder (a `%VAR%`, a packed file, a missing folder) takes the old synchronous `Navigate`. **Still on the UI thread:** every other way to open a folder (address bar, double-click in the list, Back/Forward/Up, F5, sessions, the picture viewer's next folder), because they rely on the list being filled when `Navigate` returns, and the tree's own node listings (`TreeItemViewModel.ListChildren` on expand, `SelectInTree`); a stuck folder reached that way still freezes the window. Tested with a throwaway app (a folder, a subfolder, two quick clicks (the last wins), a missing folder); not with a really stuck folder.
- **Type-ahead in the list (2026-10-19, asked by the user, as in Windows Explorer):** a letter typed with the file list in focus goes to the next item whose **displayed name** (`DisplayName`) starts with it (case ignored, the list's own sort order); the same letter again goes on to the one after (and round to the top); several letters typed less than a second apart find the first name starting with all of them, from the item the user is on. The item becomes the **only selected one** and gets the focus, so the arrow keys go on from there. `Helpers/TypeAhead` holds the decision (no controls), `MainWindow.FileListView_PreviewTextInput` the selecting. A space does not start a search; control characters (Ctrl+letter shortcuts) are left alone; nothing happens when no name matches. Tested `TypeAhead` on 12 cases with a throwaway app; **not tried in the real window**. **Not done:** the same in the folder tree, searching for a part inside a name, a visible box showing what was typed.
- **Open in Terminal / PowerShell / Command Prompt (2026-10-19, asked by the user; the existing "Open in Terminal" the user saw was Windows' own entry under More Options):** three items of our own in the right-click menu of the **tree** (the folder under the mouse; real folders and drives) and of the **list** (the one selected folder, else the folder shown; not inside an archive), in a block with a separator above them, each with the **program's own icon**. **Settings > Terminal Menu** (a group box with three checkboxes, all on by default: `AppSettings.ShowOpenInTerminal / ShowOpenInPowerShell / ShowOpenInCommandPrompt`; the box of a program that is not installed is greyed with a tooltip saying so). **A program that is not installed is never shown** (`Helpers/TerminalLauncher.IsInstalled`, looked at once per run: `cmd.exe` and Windows PowerShell in System32; Windows Terminal through its alias `%LocalAppData%\Microsoft\WindowsApps\wt.exe`, else a `wt.exe` on the PATH: Windows 10 may lack it). **How they start:** Windows Terminal `wt.exe -d <folder>` (the argument quoted by `ArgumentList`); PowerShell and the Command Prompt with `WorkingDirectory = folder` and `UseShellExecute = true` (a console window of their own, which Windows opens in Windows Terminal when that is the default). **Icons:** `IconHelper.GetIcon` of the exe; the Windows Terminal alias only has the plain window icon, so its real icon is read from `WindowsTerminal.exe` inside the package, whose folder is found in the registry (`HKCU\Software\Classes\Local Settings\...\AppModel\Repository\Packages\Microsoft.WindowsTerminal_*`, value `PackageRootFolder`; a program cannot list `C:\Program Files\WindowsApps`). It is **Windows PowerShell (powershell.exe)**, not PowerShell 7 (`pwsh`, not looked for; one more kind if wanted). **As the administrator (the user's decision, after a first version with three more items and three more checkboxes: shorter menu, nothing to choose between):** a **right-click on the menu item** opens the same terminal as the administrator (`Verb = "runas"`: Windows asks first; if the user says no, `Win32Exception` 1223 is swallowed); **Shift + click** does the same (quietly, not in the hint). WPF does nothing with a right-click on a menu item, so the items handle `PreviewMouseRightButtonUp` (`TreeCtxTerminal_RightClick`, `CtxTerminal_RightClick`: take the folder, close the menu, start); tested with a real right-click on a `ContextMenu` item in a throwaway window (the event arrives, the menu was open, it closes). Each item has the tooltip "Right-click to open it as the administrator", and the Settings group is called "Terminal Menu (Right-Click an Item to Open It as the Administrator)". An elevated program may start in System32 whatever the working folder is, so the folder is also given as an argument: `wt -d "folder"`, PowerShell `-NoExit -Command Set-Location -LiteralPath 'folder'`, the Command Prompt `/k cd /d "folder"` (a drive's root is never quoted: a closing backslash would escape the quote). Tested: availability, icons, the right-click event and the build; **no terminal was started, as a normal or as the administrator** (a window, and for Admin a UAC question, would take over the screen), and the menus were not looked at.
- **Edit the Send to menu (2026-10-19, asked by the user):** a **right-click on "Send to"** in the list's right-click menu closes that menu and shows a small one, where the mouse is, with **"Edit Send To Menu"**; clicking it opens the SendTo folder (`Environment.SpecialFolder.SendTo`, what `shell:sendto` is) **in a new tab, which becomes the active one** (`VM.OpenNewTab(folder, activate: true)`), where shortcuts are added and removed; the menu reads the folder each time it opens, so a change shows at once. WPF does nothing with a right-click on a menu item, so `MainWindow.SendToMenu_RightClick` does it (`PreviewMouseRightButtonUp`); the item has the tooltip "Right-click to edit this menu". Tested with a real mouse on a throwaway menu with a submenu item (the right-click arrives, the big menu closes, the small one opens, its item's click arrives); **not in the real window**. Only works while "Send to" is enabled (something selected, not inside an archive): a disabled menu item gets no mouse events. **The tree's menu has Send to too (2026-10-19, asked by the user, as in Explorer):** after "Reset Tree Root", `TreeSendToMenu`, filled each time the menu opens (`FillSendToMenu(menu, entries, click handler)`; the list's menu and the tree's use different click handlers); what is sent is **the folder under the mouse** (`TreeSendToItem_Click`, then the current folder is read again); disabled for a drive and for anything in an archive (`CanChangeFolder`); the same right-click "Edit Send To Menu" (`EditSendToMenu(e, bigMenu)` closes the menu it came from). Tested: sending a folder to "Compressed (zipped) Folder" through `SendToHelper` made the zip; **the tree's menu was not looked at in the real window**. Not done: the right-click on the entries inside the submenu.
- **Open in Windows Explorer (2026-10-19, item 13 of the TeraTool checklist, asked by the user):** "Open in Windows Explorer" in the right-click menu of the **tree** (the folder under the mouse; a drive too; a packed file is shown selected in its folder) and of the **list** (one selected item, else the folder shown), placed after "Open in New Tab". `MainWindow.OpenInWindowsExplorer(path)` starts `explorer.exe`: a **folder is opened**, a **file is shown selected in its folder** (`/select,"path"`, so a file in the list gives its folder with the file selected); the path is quoted when it has spaces and a drive's root (`D:\`) never is (its closing backslash would escape the quote). Disabled inside compressed files (nothing on the disk to show). Tooltip on the list's item says the selected-file behavior. **The Explorer window opens maximized** (the user's wish, 2026-10-19: `ProcessStartInfo.WindowStyle = Maximized` with `UseShellExecute`; a setting for maximized or not may come later). Checked with a real launch in a throwaway app (the folder and the `/select,` forms, a `CabinetWClass` window found by its title, `IsZoomed` true, then closed with `WM_CLOSE`); the menus were not looked at.
- **Filter bar (2026-10-19, asked by the user):** a **"Filter" toggle button** in the toolbar after New Folder (magnifier, tooltip "Filter the List by Name (Ctrl+F)"; **Ctrl+F** does the same) shows a **bar above the file list** (`FilterBar`: "Filter:", a text box, "N of M", a clear button; the list sits in a `DockPanel` under it, so the info panel's row maths is unchanged). What is typed filters the list **live**: an item stays if its **displayed name contains the text, anywhere in it, case ignored**; **several words (separated by spaces): every one must be in the name** (`alp beta` finds `Alpha Beta.doc`). Done with the list view's `Filter` (`ListCollectionView.Filter`, `MainWindow.ApplyFilter`), so sorting, selection and new files that arrive keep working; the filter is **put on the new view again whenever the sort is applied** (`ApplySort` ends with `ApplyFilter`: every tab and every folder has its own view). It stays while the bar is open, **also when another folder is opened** ("N of M" and the box say what is going on); **closing the bar (the toggle, or Esc with an empty box) clears the filter**. Keys in the box: **Esc** clears the text, a second Esc closes the bar; **Enter or Down** go on to the list (the first item gets selected if none is). The folder is still listed in full: "File 3/12" and the item count under the list follow the filtered list, the library's read marks and the other columns are untouched. Not saved between runs. Tested in the whole `MainWindow` offscreen with a throwaway app (Ctrl+F opens the bar, `alp` gives 3 of 5, `ALP beta` gives 1, `zzz` gives 0, the filter stays after F5 and a new matching file shows, closing the bar brings back everything; a render looked right); **not tried with the real mouse and keyboard**. Not done: filtering inside archives was not tried either, filtering the tree, a "match from the start" mode, saving the last filter.
- **Bookmarks (2026-10-20, asked by the user):** a **"Bookmarks" node at the top of the tree** (above Quick Access, expanded). A bookmark is an ordinary **`.lnk` shortcut** in `%AppData%\SweWolfSoftware\SwewolfFileExplorer\Bookmarks\` (`Helpers/BookmarkStore`), so it can be seen, renamed, moved and deleted in Windows Explorer; **sub-folders are groups**; the order is by name, groups first (an ordering file may come later: the user said so). Folders and files can be bookmarked (not a path inside a zip: a shortcut cannot point there). **Add:** Ctrl+D (the folder shown), "Add to Bookmarks" in the list's menu (selected items, else the folder shown) and the tree's menu; the same target is never added twice; a drive is named "Drive X"; a taken name gets " (2)". **In the tree only folder bookmarks and groups** (`FolderTabViewModel.IsTreeBookmark`; the user: files do not belong in the tree); the "Bookmarks" node and a group have the physical folder as their path, so a click shows the shortcuts in the list (file bookmarks too). A folder bookmark is a normal lazy tree node, faded when its target is gone (disk not connected). **Opening a shortcut of that folder** (`MainWindow.OpenItem` > `OpenBookmarkTarget`, `BookmarkStore.TargetOfBookmarkFile`): a folder opens in a new active tab, video and music in SweWolf Media Player, a picture in the viewer, anything else as usual; a missing target gives a message. Ctrl+D bookmarks the selected items of the list when the list has the focus, else the folder shown. **Right-click** on a bookmark or the root: a menu **built in code** (`ShowBookmarkMenu`; Open in New Tab, Rename Bookmark/Group..., Remove (to the Recycle Bin; the target is never touched), Show Bookmarks Folder). The tree reads the folder in the background (`FolderTabViewModel.ReloadBookmarks`) and again when the window is activated if anything changed (`BookmarkStore.Snapshot`). Tested: the store on 17 checks (add, twice, å ä ö, file, missing, drive, same name, group order, availability, snapshot, rename, remove, damaged .lnk), and the whole `MainWindow` in a throwaway app (node, children). **Not tried with a real mouse** (the computer was locked, `SetCursorPos` failed) and not looked at by the user yet. Not done: a Bookmarks menu in the menu bar, ordering, bookmarks inside zips.

- **Quick Access** (top of the tree): a **fixed list** made by `FolderTabViewModel.InitializeTree`, not the pinned and frequent folders of Windows' own Quick Access: Desktop, **Downloads**, Documents, Pictures, Music, Videos (Explorer's order; each only if the folder exists). The places come from Windows (`Environment.GetFolderPath`, and for **Downloads `Helpers/KnownFolders.Downloads()`**, which asks `SHGetKnownFolderPath` for `FOLDERID_Downloads`: .NET has no Downloads entry, and the user's is moved to `D:\Downloads`, so `C:\Users\<name>\Downloads` does not exist: found by the user, Downloads was missing from Quick Access; on this machine Desktop, Documents and Pictures are in OneDrive and Music and Videos on D:). Not done: letting the user choose what is in it, or showing Windows' pinned folders.
- **This PC / Quick Access clicked (2026-10-17, found by the user: the old files stayed in the grid):** they are no folder, so `MainWindow.NavigationTree_SelectedItemChanged` calls `FolderTabViewModel.ShowNoFolder()`: list, folder picture, hidden count, status label and status bar are emptied. The tab keeps its current folder (history, session file, Back/Forward unchanged); `_noFolderShown` makes F5 and the window-activated read-state refresh leave the list empty until the next `Navigate`. Tested headless (cleared, F5 stays empty, navigating lists again); not looked at in the real window.

Tested in a scratch copy with a real mouse click and keys: Esc ends the process, the menu's Close shows the Explorer (about 2 s on a normal folder; 4-8 s for a deep folder under `C:\Windows\Temp` because of the tree). **A folder on the command line** (`SwewolfFileExplorer.exe "D:\Photos"`, `App.StartupFolder`) opens the Explorer with that folder as the **root of the tree** (`MainWindow` Loaded: `VM.SetTreeRoot`, so it is the top of the tree and Up / Backspace stop there; Back to the normal tree with Reset Tree Root); a workspace/session file or a picture on the same command line wins over it. Checked with a screenshot of a scratch copy. (2) **USB DB** in the root of every drive Windows reports as **removable** (the user's external USB hard disks count, but Windows reports them as **fixed** disks (`GetDriveType` = 3, found on the user's WD Elements on E: 2026-10-15), so `LibraryService.IsOnPortableBus` also asks the disk's bus type through `IOCTL_STORAGE_QUERY_PROPERTY` / StorageDeviceProperty, `BusType` at offset 28: USB 7, 1394 4, SD 0xC, MMC 0xD; the adapter property says "unknown" for it): the hidden folder `E:\.SweWolfFileExplorerData\library.db` (folder with the Hidden attribute: Windows ignores the dot, so the attribute must be set; a folder keeps SQLite's side files out of the root and leaves room for later additions). The state then travels with the drive to another computer. A `LibraryService` decides which DB owns a path.
  - **Keys:** main DB = full path (case-insensitive); USB DB = path relative to the drive root (the letter can change); inside an archive = archive path + entry path. **Read-only media** (CD/DVD, write-protected stick): remembered in the main DB, keyed by the **volume serial number** + relative path, so the same disc is recognized in any drive. On USB use the rollback journal (not WAL), short transactions, and never keep a connection open (it would block "Safely Remove"). Give the schema a version number and document it in `docs/` (a separate TeraTool-import app will write into it: it must not be part of this app, as nobody else has TeraTool). Maybe a setting "this drive is portable" for a drive Windows reports as Fixed.
  - **Tables (only exceptions are stored; no row = unread):** `Folder` (path, sort column and direction, tree sort, cover choice, rating, tag, last opened file, own unread count as of the last visit, all-subfolders-fully-read flag) and `File` (folder, name, read, resume position, duration, rating, tag, last opened).
  - **What counts as read:** a file is read when it is **opened in the app** (Enter, double-click, Open, the picture viewer, also when paging through pictures there). Selecting it or showing its thumbnail does **not** count; unpacking an archive does not either. Files have **two states** (unread / read). A folder or archive is derived: **unread** (nothing under it opened), **partly read** (starts when the first file in it is opened) and **fully read** (every file in it **and in all its subfolders** opened). A folder never listed counts as not fully read, so a parent becomes fully read only once the whole subtree has been seen; opening a file updates its folder and then the parents through the stored counters (no scanning); a file added later makes the folder partly read again when it is next listed. Commands: Mark as Read / Unread (files and folders, folders recursive).

## Extending the App

- **New property of the tab for XAML**: the window's DataContext is `MainViewModel`, not the tab. Add the property to `FolderTabViewModel` **and** a pass-through line in `MainViewModel` (`public X Foo => _activeTab.Foo;`); the tab's change notices are forwarded for the active tab. Without it the binding fails silently (found 2026-10-17: the Rating / Expectation row stayed visible because `HasFolderMarks` was missing there).
- **New toolbar action**: add a `RelayCommand` property in `MainViewModel`, wire up `CanExecute` logic, then add a `<Button>` in `MainWindow.xaml` bound to the command.
- **New context menu item**: add a `<MenuItem>` in `MainWindow.xaml` with a `Click` handler, then call the relevant `MainViewModel` method from `MainWindow.xaml.cs`.
- **New converter**: add a class implementing `IValueConverter` in `Converters/`, register it as a resource in `MainWindow.xaml`, and use it in a `DisplayMemberBinding` or `CellTemplate`.
