# SweWolf File Explorer (SwewolfFileExplorer)

A Windows File Explorer clone built with C# (.NET 10) and WPF.

## Build & Run

```bash
dotnet build
dotnet run
```

The user tests the **Release** build: after every change run `dotnet build -c Release -p:Platform=x64` (output `bin\x64\Release\net10.0-windows\SwewolfFileExplorer.exe`), so they can run it without Visual Studio.

## Architecture

- Pattern: **MVVM**. `MainWindow.xaml.cs` handles UI events only (double-click, F2, context menu clicks) and delegates all logic to `MainViewModel`.
- NuGet packages: **TagLibSharp 2.3.0** (tags of music files; same version as FileInfoViewer), **Microsoft.Data.Sqlite** (the library) and **Svg.Skia 5.2.3** (SVG pictures, with SkiaSharp and HarfBuzzSharp: about 12 MB of native code, added 2026-10-18 with the user's approval). Packages are **not forbidden:** the user said (2026-10-15) that if a package would help, ask him at that moment; he will probably say yes. Say so in advance when a feature would need one (e.g. MetadataExtractor for image EXIF, as the sibling FileInfoViewer uses).
- Target platform: **Windows x64** (`net10.0-windows`).

## Key Design Decisions

- **Icons and speed on slow drives (2026-10-17, found by the user: opening the session `Test` took about 10 s; it holds `G:\My Drive\Music\Suno`, 618 files on Google Drive, and `D:\Downloads`):** opening that tab took 4.0 s, now 0.4 s (0.24 s the second time). Measured piece by piece (a throwaway app timing `LoadItems`, `ResolveNode` ...), the causes were: (1) **every file loaded its own icon from the disk in its own `Task.Run`** (618 at once): they held up the folder listings of the tree on the same drive. Now `FileItemViewModel.LoadIconAsync` gives a file the **icon of its type** (`IconHelper.GetIconForName`, kept per extension, no disk access, as Explorer does); only a **folder** and a file with an **icon of its own** (`IconHelper.HasOwnIcon`: exe, ico, cur, ani, lnk, url, scr, icl, cpl, msc, and any type whose registry `DefaultIcon` is `%1`) are read from the disk, in the background. The first file of a type asks `IconHelper.GetIconForNameAsync` (one background lookup per extension for all files of that type, as the first lookup of a type can take 20-50 ms when the shell loads the program that owns it); later files get the cached icon at once (`TryGetCachedIconForName`). (2) The **Type text** of each file used `IconHelper.GetFileType(path)`, which asks the disk `Directory.Exists(path)` for every file (6 ms each on Google Drive): the list now uses `GetTypeNameForName(file.Name)` (per extension). (3) The **tree** read each folder up to six times (the subfolders, then once per packed-file pattern) and asked the disk for the attributes of every folder one by one (`File.GetAttributes`, about 20 ms each on Google Drive): `TreeItemViewModel.ListChildren` now reads each folder **once** (`EnumerateFileSystemInfos`, whose entries carry their attributes), also for the expand-arrow check (`HasSubDirectories`) and `CountHiddenIn`. The same listing is what the tree showed before (checked: children, expand arrows, hidden nodes, `CountHiddenIn`). **Wait cursor:** opening a session or workspace sets `Mouse.OverrideCursor = Cursors.Wait` until the tabs are open (`MainWindow.OpenTabSet`, also for a file on the command line). Not done: opening only the active tab at once and the others when first shown (it would save more for sessions with many tabs), and a wait cursor for other slow operations.
- **A click in the tree reads the folder in the background (2026-10-19, found by the user: the program hung for 10+ minutes after a click on a tree folder):** `dotnet-stack report -p <pid>` (installed globally with the user's approval) showed the UI thread inside `FileSystemEnumerator.MoveNext` < `TreeItemViewModel.CountHiddenIn` < `FolderTabViewModel.LoadItems` < `Navigate` < `NavigationTree_SelectedItemChanged`: no CPU, no disk I/O, one folder whose listing never came back (which folder is not known). Everything in `LoadItems` ran on the UI thread. **`FolderTabViewModel.NavigateAsync(path)`** (via `MainViewModel.NavigateAsync`, used by `NavigationTree_SelectedItemChanged` only) does the disk work in `Task.Run` (`ReadListing`: subfolders, files, and the tree's hidden-folder count), with "Reading folder..." in the status bar and the old list still shown; `NavigateCore` then fills the list from that listing (`LoadItems(path, preread)`; read again if the Folders button was toggled meanwhile; an error in the read ends as the usual "Access denied" / "Error: ..." text). `_navVersion` is raised by every `Navigate` / `NavigateAsync`: a click made while an earlier listing is still being read drops the earlier one (a stuck read keeps one thread-pool thread blocked until Windows answers; the window stays usable). Anything that is not a plain existing folder (a `%VAR%`, a packed file, a missing folder) takes the old synchronous `Navigate`. **Still on the UI thread:** every other way to open a folder (address bar, double-click in the list, Back/Forward/Up, F5, sessions, the picture viewer's next folder), because they rely on the list being filled when `Navigate` returns, and the tree's own node listings (`TreeItemViewModel.ListChildren` on expand, `SelectInTree`); a stuck folder reached that way still freezes the window. Tested with a throwaway app (a folder, a subfolder, two quick clicks (the last wins), a missing folder); not with a really stuck folder.
- **Type-ahead in the list (2026-10-19, asked by the user, as in Windows Explorer):** a letter typed with the file list in focus goes to the next item whose **displayed name** (`DisplayName`) starts with it (case ignored, the list's own sort order); the same letter again goes on to the one after (and round to the top); several letters typed less than a second apart find the first name starting with all of them, from the item the user is on. The item becomes the **only selected one** and gets the focus, so the arrow keys go on from there. `Helpers/TypeAhead` holds the decision (no controls), `MainWindow.FileListView_PreviewTextInput` the selecting. A space does not start a search; control characters (Ctrl+letter shortcuts) are left alone; nothing happens when no name matches. **Esc jumped the selection to the first file (2026-10-20, found by the user):** a real Esc is also a *text* character (code 27), and WPF's own text search of the list (`ItemsControl.OnTextInput` > `TextSearch.DoSearch`) took it, found no item for it and landed on the first one (a stack trace on `SelectionChanged` in a throwaway window with a **real key press** (`keybd_event`) showed it; a key event raised in code does not reproduce it: **test keys with real input**). The list has **`IsTextSearchEnabled="False"`** now (this program has its own type-ahead above, and control characters are no longer given to anything). The folder tree was tested the same way and is not affected. Tested `TypeAhead` on 12 cases with a throwaway app; **not tried in the real window**. **The folder tree has it too (2026-10-21, asked by the user, as in Explorer):** `MainWindow.NavigationTree_PreviewTextInput` uses a second `TypeAhead`; only nodes already visible count (children of expanded nodes included, nothing is expanded by typing); the node is selected (the list follows, as for a click) and gets the focus. Compiled only, not tried in the real window. **Not done:** searching for a part inside a name, a visible box showing what was typed.
- **M3U playlists as folders (2026-10-21, asked by the user; read-only first, editing comes later):** `.m3u` / `.m3u8` files are in the **tree after the folders** (with the packed files; `TreeItemViewModel.IsPlaylist`, **no expand arrow**, `IsTreeFile` = packed file or playlist, used by every tree listing), and **opening one** (click in the tree, Enter / double-click in the list when the Folders button is on, the address bar) shows **its files in the grid, in the order of the list** (`FolderTabViewModel.LoadPlaylistItems`; the path of the "folder" is the .m3u file itself). `Helpers/PlaylistFile.Read`: text by `TextFiles` (BOM, UTF-8, else ANSI), `#` lines, empty lines and web addresses skipped, `file:///` understood, a relative path starts in the playlist's folder; the same file twice is shown twice. **The items are real files** (real paths, `IsInArchive` false): icon, type, size, dates, preview, tags, Length / Bitrate / Dimensions, opening, double-click and the Play bar's playlist all work as for files in a folder. **A line whose file is missing** is shown dimmed (`IsMissing`, `IsHidden`; type "Missing file") and **never played** (`PlaylistInList` skips it). **No sort until a header is clicked** (`SortColumn.None`, the sort chosen is remembered for that playlist like for any folder). **Read-only:** `_inArchive` is true (so Delete, Cut, Paste, Rename, New Folder, Send to, Properties are off, as in an archive) and `_inPlaylist` / `InPlaylist` says which kind; tags are still read (`EnsureTags`). **Entering a playlist shows the Play bar** (`MainWindow`'s `VM.PropertyChanged` on `InPlaylist`; leaving it does not hide it), so a double-click plays on along the list (Slide Show mode). **The Play bar closes again when a folder is shown, but only if the playlist opened it** (`_playBarOpenedByPlaylist`; a bar the user opened, or toggled by hand meanwhile, stays; not closed while a run is playing, so Pause stays reachable). **No next folder after a playlist (the user's rule):** at the end of a run from a playlist (`_runInPlaylist`, picture viewer `IsPlaylist`) the question has only **Start from Beginning / Close** (an end action of Go to Next Folder means Close; no folder search). Not watched for changes (F5 reads it again). Tested headless with a throwaway app (entries with comments, a relative path in a sub-folder, a missing file, a web address, an absolute path; `InPlaylist`, the items, the dimmed missing one, the Play bar shown, the tree node found and selected with no children, back in a folder); **not looked at in the real window.** **Not done:** editing (the user's plan: Delete = remove from the playlist, Paste = add an entry), ratings and read marks (bold) of the items (the library state is read per folder, which a playlist is not), `#EXTINF` titles, streams, other formats (pls, wpl), a Folder column, playlists inside archives, next-folder search through playlists, "Show in Windows Explorer" for an item.
- **Editing a playlist (2026-10-21, asked by the user, from TeraTool's playlist buttons; the screenshot did not reach me, so the order is my choice):** while a playlist is shown the **playlist buttons** sit in the info line, to the right of "File 14/15" and the hidden-items link (`PlaylistBar`, a `StackPanel` there, 22 px high; moved there from a bar above the list at the user's wish, 2026-10-21; `MainWindow.Playlist.cs`): **Add Files...** (a file box, several files, put after the last selected entry), **Move Up** and **Move Down** (only a filled arrow, with the tooltip), (20 px high with room under them, and 130 px to the right of "File 14/15", the user's wish; **Save Playlist As... suggests the name of the folder the playlist is in** + its extension), **Save Playlist** (enabled only when there are changes; Ctrl+S) and **Save Playlist As...** (writes the new file, then opens it; the old file stays as it was). **Moving** works on all selected entries (the ones that can move do); **the first move ends the sort by a column**: the order shown at that moment becomes the playlist's own order (`SetPlaylistOrderFrom`, then `ApplySort(None)`), and a sort chosen later by clicking a header still works for viewing. **Delete / the menu's "Remove from Playlist"** takes the selected entries out of the list (the files are never touched); **Ctrl+V / Paste** adds the copied files as entries after the selected one (only files; a folder on the clipboard is ignored with a message; Cut and Delete of files stay off). Changes are **kept in memory until saved** (`PlaylistDirty`): leaving the playlist (another folder, This PC, closing the tab or the program) asks "Do you want to save the changes to the playlist?" Yes / No / Cancel (`ConfirmLeavePlaylist`); F5 says to save first. `PlaylistFile.Write`: UTF-8 without a byte order mark, CRLF, `#EXTM3U` first, **paths relative to the playlist's folder when the file is in it or below it, else full**, the `#EXTINF` line of an entry is kept with it (`FileItemViewModel.PlaylistInfo`); a missing file's line is kept too; written to a temporary file and swapped in. Tested headless (move up / down with several, the top stays, add with a folder ignored, remove, save and read back with the info kept, save as from another folder); **the bar and the dialogs were not looked at in the real window.** **Create Playlist...** is in the right-click menus of the list (the folder shown) and the tree (the folder under the mouse): first the question "Which files should the new playlist start with?" (`ChoiceDialog` with `fontSize: 16`: at its usual 22 the four equally wide buttons were wider than the dialog and the texts were cut off; the dialog may now grow up to the width of the screen) (**All Files in the Folder** = the files the Play bar can play, pictures / music / video, in the list's order when the folder is the one shown, else by name; **Selected Files**, off when nothing is selected, the list's menu only; **No Files**; **Cancel**), then the name (**suggested: the name of the folder**, with (2), (3) if taken; "Playlist" for a drive; the file is `<name>.m3u8`, UTF-8, in that folder; a taken name is refused), then the new playlist is opened so files can be added at once. The dialogs were not tried by hand; the info line was rendered offscreen. **A playlist in the tree can be renamed and deleted** (the tree's menu, F2 and Delete; `CanRenameOrDelete`; the rename box has the extension in its own box, **read-only** (`InputDialog`'s `extensionReadOnly`; the user's wish); Delete goes to the Recycle Bin after the usual question; renaming the playlist that is shown opens it under the new name; both ask first when the shown playlist has unsaved changes). Rename was tested headless; Delete was not tried. Not done: dragging entries to reorder, a title for the playlist, adding a folder's files, streams, undo.
- **Open in Terminal / PowerShell / Command Prompt (2026-10-19, asked by the user; the existing "Open in Terminal" the user saw was Windows' own entry under More Options):** three items of our own in the right-click menu of the **tree** (the folder under the mouse; real folders and drives) and of the **list** (the one selected folder, else the folder shown; not inside an archive), in a block with a separator above them, each with the **program's own icon**. **Settings > Terminal Menu** (a group box with three checkboxes, all on by default: `AppSettings.ShowOpenInTerminal / ShowOpenInPowerShell / ShowOpenInCommandPrompt`; the box of a program that is not installed is greyed with a tooltip saying so). **A program that is not installed is never shown** (`Helpers/TerminalLauncher.IsInstalled`, looked at once per run: `cmd.exe` and Windows PowerShell in System32; Windows Terminal through its alias `%LocalAppData%\Microsoft\WindowsApps\wt.exe`, else a `wt.exe` on the PATH: Windows 10 may lack it). **How they start:** Windows Terminal `wt.exe -d <folder>` (the argument quoted by `ArgumentList`); PowerShell and the Command Prompt with `WorkingDirectory = folder` and `UseShellExecute = true` (a console window of their own, which Windows opens in Windows Terminal when that is the default). **Icons:** `IconHelper.GetIcon` of the exe; the Windows Terminal alias only has the plain window icon, so its real icon is read from `WindowsTerminal.exe` inside the package, whose folder is found in the registry (`HKCU\Software\Classes\Local Settings\...\AppModel\Repository\Packages\Microsoft.WindowsTerminal_*`, value `PackageRootFolder`; a program cannot list `C:\Program Files\WindowsApps`). An elevated program may start in System32 whatever the working folder is, so the folder is also given as an argument: `wt -d "folder"`, PowerShell `-NoExit -Command Set-Location -LiteralPath 'folder'`, the Command Prompt `/k cd /d "folder"` (a drive's root is never quoted: a closing backslash would escape the quote). Tested: availability, icons, the right-click event and the build; **no terminal was started, as a normal or as the administrator** (a window, and for Admin a UAC question, would take over the screen), and the menus were not looked at.

## Extending the App

- **New property of the tab for XAML**: the window's DataContext is `MainViewModel`, not the tab. Add the property to `FolderTabViewModel` **and** a pass-through line in `MainViewModel` (`public X Foo => _activeTab.Foo;`); the tab's change notices are forwarded for the active tab. Without it the binding fails silently (found 2026-10-17: the Rating / Expectation row stayed visible because `HasFolderMarks` was missing there).
- **New toolbar action**: add a `RelayCommand` property in `MainViewModel`, wire up `CanExecute` logic, then add a `<Button>` in `MainWindow.xaml` bound to the command.
- **New context menu item**: add a `<MenuItem>` in `MainWindow.xaml` with a `Click` handler, then call the relevant `MainViewModel` method from `MainWindow.xaml.cs`.
- **New converter**: add a class implementing `IValueConverter` in `Converters/`, register it as a resource in `MainWindow.xaml`, and use it in a `DisplayMemberBinding` or `CellTemplate`.
