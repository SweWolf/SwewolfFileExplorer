# SweWolf File Explorer (SwewolfFileExplorer)

A Windows File Explorer clone built with C# (.NET 10) and WPF.

## Build & Run

```bash
dotnet build
dotnet run
```

The user tests the **Release** build: after every change run `dotnet build -c Release -p:Platform=x64` (output `bin\x64\Release\net10.0-windows\SwewolfFileExplorer.exe`), so they can run it without Visual Studio.

## Architecture

- Pattern: **MVVM**. `MainWindow.xaml.cs` handles UI events only (double-click, F2, context menu clicks) and delegates all logic to `MainViewModel`.
- NuGet packages: **TagLibSharp 2.3.0** (tags of music files; same version as FileInfoViewer), **Microsoft.Data.Sqlite** (the library) and **Svg.Skia 5.2.3** (SVG pictures, with SkiaSharp and HarfBuzzSharp: about 12 MB of native code, added 2026-10-18 with the user's approval). Packages are **not forbidden:** the user said (2026-10-15) that if a package would help, ask him at that moment; he will probably say yes. Say so in advance when a feature would need one (e.g. MetadataExtractor for image EXIF, as the sibling FileInfoViewer uses).
- Target platform: **Windows x64** (`net10.0-windows`).

## Key Design Decisions

- **Icons and speed on slow drives (2026-10-17, found by the user: opening the session `Test` took about 10 s; it holds `G:\My Drive\Music\Suno`, 618 files on Google Drive, and `D:\Downloads`):** opening that tab took 4.0 s, now 0.4 s (0.24 s the second time). Measured piece by piece (a throwaway app timing `LoadItems`, `ResolveNode` ...), the causes were: (1) **every file loaded its own icon from the disk in its own `Task.Run`** (618 at once): they held up the folder listings of the tree on the same drive. Now `FileItemViewModel.LoadIconAsync` gives a file the **icon of its type** (`IconHelper.GetIconForName`, kept per extension, no disk access, as Explorer does); only a **folder** and a file with an **icon of its own** (`IconHelper.HasOwnIcon`: exe, ico, cur, ani, lnk, url, scr, icl, cpl, msc, and any type whose registry `DefaultIcon` is `%1`) are read from the disk, in the background. The first file of a type asks `IconHelper.GetIconForNameAsync` (one background lookup per extension for all files of that type, as the first lookup of a type can take 20-50 ms when the shell loads the program that owns it); later files get the cached icon at once (`TryGetCachedIconForName`). (2) The **Type text** of each file used `IconHelper.GetFileType(path)`, which asks the disk `Directory.Exists(path)` for every file (6 ms each on Google Drive): the list now uses `GetTypeNameForName(file.Name)` (per extension). (3) The **tree** read each folder up to six times (the subfolders, then once per packed-file pattern) and asked the disk for the attributes of every folder one by one (`File.GetAttributes`, about 20 ms each on Google Drive): `TreeItemViewModel.ListChildren` now reads each folder **once** (`EnumerateFileSystemInfos`, whose entries carry their attributes), also for the expand-arrow check (`HasSubDirectories`) and `CountHiddenIn`. The same listing is what the tree showed before (checked: children, expand arrows, hidden nodes, `CountHiddenIn`). **Wait cursor:** opening a session or workspace sets `Mouse.OverrideCursor = Cursors.Wait` until the tabs are open (`MainWindow.OpenTabSet`, also for a file on the command line). Not done: opening only the active tab at once and the others when first shown (it would save more for sessions with many tabs), and a wait cursor for other slow operations.
- **Async icon loading**: `FileItemViewModel.LoadIconAsync()` fetches shell icons on a background thread and marshals back to the UI dispatcher. This keeps the list responsive when navigating large folders.
- **Quick Access** (top of the tree): a **fixed list** made by `FolderTabViewModel.InitializeTree`, not the pinned and frequent folders of Windows' own Quick Access: Desktop, **Downloads**, Documents, Pictures, Music, Videos (Explorer's order; each only if the folder exists). The places come from Windows (`Environment.GetFolderPath`, and for **Downloads `Helpers/KnownFolders.Downloads()`**, which asks `SHGetKnownFolderPath` for `FOLDERID_Downloads`: .NET has no Downloads entry, and the user's is moved to `D:\Downloads`, so `C:\Users\<name>\Downloads` does not exist: found by the user, Downloads was missing from Quick Access; on this machine Desktop, Documents and Pictures are in OneDrive and Music and Videos on D:). Not done: letting the user choose what is in it, or showing Windows' pinned folders.
- **This PC / Quick Access clicked (2026-10-17, found by the user: the old files stayed in the grid):** they are no folder, so `MainWindow.NavigationTree_SelectedItemChanged` calls `FolderTabViewModel.ShowNoFolder()`: list, folder picture, hidden count, status label and status bar are emptied. The tab keeps its current folder (history, session file, Back/Forward unchanged); `_noFolderShown` makes F5 and the window-activated read-state refresh leave the list empty until the next `Navigate`. Tested headless (cleared, F5 stays empty, navigating lists again); not looked at in the real window.
- **Start on This PC (2026-10-17, asked by the user):** the program starts with one tab on **This PC**: node selected, no drive expanded, empty list (Quick Access above shows its places as always). `FolderTabViewModel.ShowThisPc()` (a tab made with a null start path; title "This PC", `FolderPath` empty). **A new tab (Ctrl+T, Ctrl+N, the "+" button) always starts on This PC, never in the folder of the active tab** (the user's decision 2026-10-18; This PC is the default node, a setting for it may come later; "Open in New Tab" of a folder, and middle-click on one, still open that folder); a session/workspace tab saved with an empty path is restored as This PC. Before, the start folder was the user profile. Back does not return to This PC (the empty "folder" is not put in the history). Tested headless; not looked at in the real window.
- **Starting with a picture on the command line (2026-10-17, asked by the user, as TeraTool did):** `SwewolfFileExplorer.exe "D:\Photos\a.jpg"` (any `ThumbnailLoader.IsImage` file) opens **only the picture viewer**, full screen, with no Explorer window on screen. `App.xaml` has **no `StartupUri` any more**: `App.OnStartup` makes `MainWindow` itself and either shows it or, with a picture, calls `MainWindow.RunPictureOnly` (from the dispatcher, `ShutdownMode.OnExplicitShutdown` until the Explorer is shown). The picture list is `MainWindow.QuickPictureList`: the folder's pictures in the folder's saved sort (else Name), hidden files left out, **without opening the folder in the Explorer** (doing that first cost seconds: it expands the tree to the folder; the Explorer navigates there only when it is shown). **Esc, X, Alt+F4 and the window's close button end the whole program; "Close" in the viewer's right-click menu goes on to the Explorer** in the folder of the picture last shown, with that picture selected (`PictureViewerWindow.ExitApplication`, false only after the menu's Close; the end-of-list dialog's Close is an Esc). **Hourglass while the Explorer loads (asked by the user):** the menu's Close does not close the viewer at once; `PictureViewerWindow.CloseToExplorerHandler` asks `MainWindow.RunPictureOnly` to get the Explorer ready (navigate, `Show()`), with `Mouse.OverrideCursor = Wait`, and the viewer stays on screen until the Explorer's `ContentRendered`, then closes and the cursor is cleared (an hourglass could not be shown after the viewer closed: no window of ours would be under the mouse). Checked with `GetCursorInfo` in a scratch copy: Wait during the load (0.9 s on a normal folder, 9 s on a deep temp folder), normal afterwards. The viewer reads the library like always (the pictures shown are marked read). Tested in a scratch copy with a real mouse click and keys: Esc ends the process, the menu's Close shows the Explorer (about 2 s on a normal folder; 4-8 s for a deep folder under `C:\Windows\Temp` because of the tree). **A folder on the command line** (`SwewolfFileExplorer.exe "D:\Photos"`, `App.StartupFolder`) opens the Explorer with that folder as the **root of the tree** (`MainWindow` Loaded: `VM.SetTreeRoot`, so it is the top of the tree and Up / Backspace stop there; Back to the normal tree with Reset Tree Root); a workspace/session file or a picture on the same command line wins over it. Checked with a screenshot of a scratch copy. Not done: other file types (open the player / the default program), several arguments at once, a picture inside an archive, passing a path to an already running copy (every start is a new process).
- **Hide extensions of special shell file types (2026-10-17, asked by the user, from a list of Windows' `NeverShowExt` types):** Settings > File Names > "Hide Extensions for Special Shell and System File Types" (`AppSettings.HideShellExtensions`, **on by default**, as Windows). `Helpers/ShellExtensions` holds the list (`.lnk .pif .url .scf .desklink .mapimail .mydocs .library-ms .searchconnector-ms`, hard-coded as in the screenshot, not read from the registry): `FileItemViewModel.DisplayName` (what the Name column shows; `Name` stays the real file name and is what sorting and every path use) is the name without that extension. **Rename** (F2, menu) starts with the name without it and puts it back (`RestoreExtension`, also when the user typed it). Only the last extension counts (`Tricky.lnk.txt` is unchanged); case is ignored. The list is refreshed after the Settings dialog (other tabs update when they are read again). Tested the helper (10 checks) and a scratch copy's list (Photos, Site, Old, My Library without the extension; Notes.txt and Tricky.lnk.txt unchanged). Not done: the same for the tree's packed files (they keep their extension on purpose), reading the list from the registry, and the Rename box itself was not tried by hand.
- **Windows menu, "More Options" (2026-10-17, asked by the user, planned together first):** our own right-click menus stay; they got a last item **More Options** (list menu: the selected items, or the shown folder when nothing is selected **or the click was on the empty part of the list**; tree menu: that folder) and **Shift + right-click** opens the same at once (list, empty area, tree), as in Explorer. It is the **real Windows menu** with every shell extension (7-Zip, PowerRename, File Locksmith, Image Resizer, Open with, Send to, Cast to Device, Ask Copilot, Open with Code ...). `Helpers/ShellContextMenu`: `SHParseDisplayName` > `SHBindToParent` > `IShellFolder.GetUIObjectOf` (several items: one parent folder) or `CreateViewObject` on the folder itself (empty area) > `IContextMenu.QueryContextMenu` (`CMF_EXTENDEDVERBS`) into a popup menu, shown with `TrackPopupMenuEx` at the mouse, `InvokeCommand` (`CMINVOKECOMMANDINFOEX`, with the point) for the chosen line. **Own thread** (STA) with a hidden `HwndSource` as the owner, which forwards `WM_INITMENUPOPUP / DRAWITEM / MEASUREITEM / MENUCHAR` to `IContextMenu2/3` (that fills Send to, Open with, 7-Zip when they open and draws owner-drawn items): a slow extension cannot freeze the window; only one menu at a time. With a dark style (Cyber too) the menu is dark (`uxtheme.dll` ordinals 135 / 136, `SetPreferredAppMode(ForceDark)` + `FlushMenuThemes`; light styles force light). **Hide list** (`AppSettings.HiddenShellMenuItems` in `settings.json`, no window for it; verbs or texts, any case): `cut;copy;delete;rename;properties;open;copyaspath;paste;undo;Add to Favorites`: the app has its own of those (they keep the library right); Cast to Device, Ask Copilot and File Locksmith are shown on purpose (the user wanted to see them). **Never `CMF_EXTENDEDVERBS` (Explorer's Shift menu; found by the user, 2026-10-18):** for a **folder** it makes the Send to submenu list every folder of the user profile after the normal items (23 lines here: `.nuget`, `.claude`, `.vscode` ...); a file does not get them; the lines it adds (Copy as path) are hidden anyway. So Shift + right-click opens the same plain Windows menu as "More Options" (`ShellContextMenu`'s `extended` parameter stays for tests only). Cost seen: the first Windows menu of a run takes about 2 s (the shell extensions load), later ones about 0.3 s. Windows lists some items twice (File Locksmith, PowerRename, Image Resizer: its modern and its classic entry), as in Explorer. After a command the folder is read again (selection kept) and once more when the window comes back to the front (`_refreshOnActivate`: 7-Zip etc. finish in another process). Not available inside compressed files and for This PC / Quick Access. Tested: the menu of a text file, a picture, two files, a folder, a drive and the folder background built headless (19-28 lines each) and `link` (Create shortcut) invoked by verb (the shortcut appeared); in a scratch copy with a real mouse: More Options, Shift + right-click, the Send to submenu filled, the empty-area menu (New ...), the tree folder menu, all dark. Clicking an item in the real window was not tried by hand except through the verb test. Not done: our own themed rendering of these items, a Settings window for the hide list, removing the double entries.
- **A picture dragged in from a web browser (2026-10-18, asked by the user):** drop an image from Chrome / Edge / Firefox on the **file list** (it goes into the shown folder) or on a **folder of the tree** (that folder) and it becomes a file there, with its original name; a name that is taken gets " (2)", " (3)" ... (`FileMode.CreateNew`: **never overwrites**). `Helpers/DroppedImage`: a real Chrome drag was probed (a throwaway drop window): the formats are `FileGroupDescriptorW` (the name, `a.png`), `FileContents` (**WPF's `GetData` returns null for it: it is read through the raw COM `IDataObject` with `lindex` 0**, stream or HGLOBAL), `UnicodeText` / `UniformResourceLocator(W)` (the web address), `HTML Format`. The bytes are used when the browser gives them; otherwise the picture is **downloaded** from the address (`HttpClient`, 60 s, at most 200 MB; `data:image/...` addresses too). The extension is made to fit the real picture (first bytes: png, jpg, gif, webp, bmp, avif, ico, tif, svg; else the content type; else `.jpg`). The data object is only valid inside the Drop handler, so `Read` takes everything out there and `SaveAsync` runs after. `MainWindow`: `FileListView_DragOver/Drop`, `NavigationTree_DragOver/Drop` (`TreeFolderUnder`), `SavePicture` (wait cursor, the folder is read again and the new file selected when it is the shown one, a message in the title bar: "Saved a.png"; a failure is a message box). Only real folders (not This PC, not inside a compressed file) and only pictures: **files dragged from Explorer are not handled** (`FileDrop` is refused; a later feature: copy / move by drag). Tested with a real Chrome (isolated profile) dragged by mouse onto the list twice (a.png, then a (2).png, the new file selected) and onto a tree folder (the file went into that folder). The download fallback was not exercised (the first formats worked).
- **Windows variables in the address bar (2026-10-17, asked by the user):** `%APPDATA%`, `%TEMP%`, `%USERPROFILE%`, `%ProgramFiles%` ... (any environment variable, any case), also with a path after them (`%APPDATA%\Microsoft`, `%windir%/System32`), are expanded at the top of `FolderTabViewModel.Navigate` (`Environment.ExpandEnvironmentVariables`, the result tidied with `GetFullPath`; the address bar then shows the real path). A folder literally named with `%` wins; an unknown variable ends as "Path not found". Not done: Explorer's `shell:` names (`shell:Startup`) and the other special places Explorer knows (Recycle Bin, Control Panel).
- **Focus frame of the address bar (2026-10-17, asked by the user):** the toolbar's text box style shows no focus at all, and its border does not react to `BorderBrush` triggers (tried: nothing changed; a style without `BasedOn` the toolbar's turned the box white). The Fluent box also draws a thicker line along its bottom edge when not focused (looked 3D; the user wanted it flat). So the `AddressBar` has its own flat `ControlTemplate` (background + `PART_ContentHost`, no border) and sits in a `Border`: 1 px `LineBrush`, and 2 px in the accent color (`SystemColors.AccentColorBrushKey`, padding 1 to 0 so the size stays) while `IsKeyboardFocusWithin` is true. Checked by screenshots of a scratch copy with and without F6.
- **Lazy tree loading**: `TreeItemViewModel` adds a dummy child on init so the expand arrow appears. On first expand, `LoadChildren()` replaces the dummy with real subdirectories.
- **Clipboard**: Cut / Copy / Paste use the **Windows clipboard** (`Helpers/FileClipboard`: a file drop list plus "Preferred DropEffect", Copy = 1, Move = 2, as Explorer does), so files go to and come from Explorer and other instances. Copy of something inside an archive unpacks it first to the temp folder (`RealPathOf` / `ExtractToTemp`; gone when the app ends). Paste is enabled when the clipboard holds files (`FileClipboard.HasFiles`). After a cut-paste the clipboard is cleared, as Explorer does; moving a folder to another drive copies, then deletes (`MoveDirectory`). Cut items are not faded in the list (not done).
- **Column layout**: right-click a column header for a checklist of columns and "More..." (Choose Details dialog: order, show/hide, width). Hidden columns are kept in `MainWindow`'s `_layout` list and removed from the GridView. The layout is saved on every change and on close in `%AppData%\SweWolfSoftware\SweWolf File Explorer\columns.json` (`ColumnLayoutStore`).
- **Tree follows the folder**: every navigation (list, address bar, back/up) expands the tab's tree to the folder and selects its node (`SelectInTree`). A node selected this way is remembered in `_programmaticSelection`, so the window does not treat it as a click and navigate again.
- **Folders in the list**: hidden by default (they are in the tree); the "Folders" toggle button in the toolbar shows them. `SharedState.ShowFolders`, saved in `settings.json` (`AppSettingsStore`) next to `columns.json`. `FolderTabViewModel.Refresh()` also re-reads the current folder's tree node, so new, renamed or deleted folders show in the tree.
- **Font size**: Ctrl + mouse wheel over the list or over the tree changes that control's font size (8-40 pt, default 13), separately. The new size is flashed in the title bar for 2.5 s and saved in `settings.json` (`ListFontSize`, `TreeFontSize`). Always save through the one settings object, `AppSettingsStore.Current` (`SharedState.Settings` is the same instance), so one setting never overwrites another.
- **Name**: the app is called "SweWolf File Explorer" in the UI (`AppInfo.Name`, main window title); "My File Explorer" was a beta name. The settings folder is `%AppData%\SweWolfSoftware\SweWolf File Explorer` (`AppInfo.Name`; settings of the beta name were not moved). The EXE, project, namespace and repository are `SwewolfFileExplorer` (renamed from MyFileExplorer before any release).
- **About**: **Help > About** (`Views/AboutWindow`, as in the siblings: blue banner with icon, version from the assembly and "latest version" check against GitHub Releases `SweWolf/SwewolfFileExplorer`, silent when offline or when there is no release yet). The version is `<Version>` in the .csproj. Help has no "SweWolf File Explorer Help" item yet (no help file).
- **Menu, Settings, Create Shortcut**: the menu bar has **Tools > Create Shortcut...** (desktop / Start menu, current or all users; `Views/CreateShortcutWindow`, as in the sibling apps, but without "Send To" until the app accepts a folder on the command line) and **Tools > Settings** (`Views/SettingsWindow`: Appearance > Style: Light / Dark / System / Cyber Cyan, default System, saved as `Style` in `settings.json`). Message boxes of these windows use `AppInfo.Name` as caption (older ones still say "Error").
- **Cyber Cyan style** (named by the user 2026-10-18; it was "Cyber", an old `settings.json` value `Cyber` is read as `Cyber Cyan`; the code names `CyberText`, `ApplyCyberColors` are unchanged): the Dark theme with black backgrounds and light blue text (#ADD8E6, the colors of the old TeraTool). `ThemeService.ApplyCyberColors` replaces the theme's own white-text and window-background brushes by name in `Application.Resources` and removes them again when another style is chosen.
- **Hidden items**: files and folders with the Hidden or System attribute are not listed. A line under the list says "N hidden items (click to show)" and toggles them for the current folder (`FolderTabViewModel._showHidden`, reset on every navigation, kept on refresh); shown ones are faded (`FileItemViewModel.IsHidden`). **Inside compressed files** a second list applies on top of the first (`AppSettings.HiddenExtensionsInArchives`, Settings > Hidden Files > "Also Hide Files with These Extensions When Inside Compressed Files", empty by default; `HiddenItems.IsHiddenInArchive`, used by the list, the read-state and the next-folder search): e.g. the nfo / txt files that come with a comic.
- **Archives (.zip, .cbz read by .NET; .rar, .cbr, .7z read by 7-Zip)** (`Helpers/ArchiveSupport`; `ArchiveReader` has one implementation per way of reading: `ZipReader` and `SevenZipReader`; `Helpers/SevenZipRunner` runs `7z.exe`: `l -slt -ba` lists, `e -so -spd` writes one file to the output, so RAR/7z are read in place too, like zip; 7-Zip is found through the registry (`HKLM`/`HKCU` `SOFTWARE\7-Zip`), Program Files, then the PATH; without it entering a RAR shows "7-Zip is needed ..." in the status bar; every call passes a dummy `-p` password, so an archive that needs a password fails at once with a clear message instead of 7-Zip waiting for input; an archive inside another one: a zip is read into memory, anything else is unpacked once to `%TEMP%\SwewolfFileExplorer\<pid>\nested\`; any mix works: zip in RAR, RAR in zip ...; a RAR that stores no date shows the date of the archive file; a **solid** RAR is slow for one picture after another, as 7-Zip must decode what comes before it). A packed file is a folder. In the tree the archives come after all the folders, with their extension (`TreeItemViewModel.IsArchive`; always an expand arrow, as looking inside costs a read); Enter / double-click on one in the list enters it; the address bar takes `D:\Photos\Trip.zip\Day 1`, and a zip inside a zip works (`...\All.zip\Trip.zip\Day 1`). They are read **in place** (`System.IO.Compression`, nothing is unpacked to browse); an index per archive is cached (`GetIndex`, invalidated by F5 / `Refresh`). Every path in the app can be such a path: `FileItemViewModel.IsInArchive` makes the icon and type come from the name (`IconHelper.GetIconForName`, cached per extension); `ArchiveSupport.OpenAnyFile` is what `PictureLoader` / `ThumbnailLoader` read through, so the viewer and the thumbnail work on pictures inside archives. A file opened from an archive is unpacked to `%TEMP%\SwewolfFileExplorer\<pid>\<guid>\` first (`FolderTabViewModel.RealPathOf`; removed at exit, stale ones at start). **Read-only:** inside an archive Cut, Delete, Rename, New Folder, Paste, Send to and Properties are disabled (`FolderTabViewModel.InArchive`); Copy then Paste into a real folder unpacks (files, folders, a zip inside a zip as the file). **Sort inside an archive:** by default none (`SortColumn.None`, the view has no `CustomSort`): the files show in the order they are stored in the zip, with no arrow in a header, as in TeraTool; a click on a header sorts (and is remembered for that folder like any folder's sort). Real folders still default to Name. The same for the tree: the folders (then the zips) inside an archive show in stored order until a sort is chosen in the tree's Sort By box, which is then empty (`SharedState.GetTreeSort` gives `None`, `TreeSortIndex` -1); choosing a column or a direction there sorts them. A folder or archive is derived: **unread** (nothing under it opened), **partly read** (starts when the first file in it is opened) and **fully read** (every file in it **and in all its subfolders** opened). A folder never listed counts as not fully read, so a parent becomes fully read only once the whole subtree has been seen; opening a file updates its folder and then the parents through the stored counters (no scanning); a file added later makes the folder partly read again when it is next listed. ## Extending the App

- **New property of the tab for XAML**: the window's DataContext is `MainViewModel`, not the tab. Add the property to `FolderTabViewModel` **and** a pass-through line in `MainViewModel` (`public X Foo => _activeTab.Foo;`); the tab's change notices are forwarded for the active tab. Without it the binding fails silently (found 2026-10-17: the Rating / Expectation row stayed visible because `HasFolderMarks` was missing there).
- **New toolbar action**: add a `RelayCommand` property in `MainViewModel`, wire up `CanExecute` logic, then add a `<Button>` in `MainWindow.xaml` bound to the command.
- **New context menu item**: add a `<MenuItem>` in `MainWindow.xaml` with a `Click` handler, then call the relevant `MainViewModel` method from `MainWindow.xaml.cs`.
- **New converter**: add a class implementing `IValueConverter` in `Converters/`, register it as a resource in `MainWindow.xaml`, and use it in a `DisplayMemberBinding` or `CellTemplate`.
